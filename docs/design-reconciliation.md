# 디자인 시스템 재조정 — 판정 로그

세 문서의 역할을 갈라 둔다.

| 문서 | 답하는 질문 |
|---|---|
| `design-carryover.md` | 흡수로 **무엇이 사라졌나** (인벤토리, G1~G33) |
| **이 문서** | 그 각각을 **어떻게 할 것인가** (판정 · 계층 · 진행) |
| `design-system.md` | 최종적으로 **무엇이 규격인가** (구현과 일치해야 하는 계약) |

목표는 예전 브랜치의 복원이 아니다. **최신 기능 구조를 유지한 채, 쓸 만한 디자인 시스템
결정만 골라 올바른 계층에 다시 세우는 것**이다. 예전 구현이 자동으로 더 낫다고 보지 않는다.

## 판정 어휘

- **KEEP CURRENT** — 현재 구현이 더 적절하다
- **RESTORE** — 예전 결정을 되살린다 (구현까지 거의 그대로 쓸 수 있다)
- **REIMPLEMENT** — 의도는 맞지만 예전 구현을 복사하지 않는다. 현재 아키텍처로 다시 세운다
- **DROP** — 더는 쓸모가 없거나 불필요한 갈래를 만든다
- **DEFER** — 영향 범위가 커서 별도 승인이 필요하다

## 계층 (Systemize)

`token` → `primitive` → `component` → `layout` → `page` → `doc`(문서만)

**한 화면씩 값을 되살리지 않는다.** 재사용되는 규칙이면 공유 계층에 넣는다.

## 2. 문서-구현 불일치 — 먼저 해소한다

`design-system.md` 는 governing reference 인데, **표준으로 적힌 컴포넌트 상당수가 코드에
없다.** 문서가 앞서 나간 상태이므로 문서도 재조정 대상이다.

### 문서에는 표준인데 코드에 없는 것

| 이름 | 문서 위치 | 처리 |
|---|---|---|
| `LayoutCards` `LayoutFeatures` `LayoutHorizCards` `LayoutColumns` `LayoutTextColumns` `LayoutAlternating` `LayoutSticky` (Layout 1~7) | §4 레이아웃 모듈 표 | **문서에서 제거** (G19 DROP) |
| `CenterHeading` | §4 | 문서에서 제거 |
| `OverviewCards` `FacilityCard` `LabeledList` | §3 스팬 표 · §4 | 문서에서 제거 — 실제로는 `FeatureList`·`TitledCard`·`StatCards` 가 그 자리를 맡고 있다 |
| `ComparisonTable` | §4 「**모든 수치·데이터 표의 표준**」 | G17 로 재설계 — 표준을 지정했는데 물건이 없는 상태가 가장 위험하다. `StepConfigOptions.tsx:214` 주석도 이 이름을 참조한다 |

다시 쓴다. 문서가 실제 시스템을 설명하지 못하면 다음 작업자가 또 국소 규칙을 만든다.

## 3. G1~G33 판정

| # | 항목 | 판정 | 계층 | 근거 |
|---|---|---|---|---|
| G1 | 버튼 호버 = 옐로 면 | **KEEP CURRENT** (판정 정정) | doc | **「호버 피드백이 아예 없다」는 근거가 틀렸다.** `btnClass` 의 네 변형이 모두 호버를 갖고 있다 — `primary` 한 단 진한 검정 · `secondary` 검정 채움 반전 · `tertiary` 밑줄 · `danger` 빨강 채움(`kit.tsx` `BTN_VARIANT`). 이미 한 곳에 모여 일관적이다. 옐로 통일은 브랜드 표현 변경이라 요청 없이 바꾸지 않고, 현재 규칙을 문서에 명문화했다 |
| G2 | 버튼 사이즈 스케일 | **KEEP CURRENT** | — | 예전은 `md`·`lg` 에 `text-base`(16)를 썼는데, 같은 브랜치가 「16은 푸터 전용」이라고 정해 놓았다 — 자기 규칙과 모순. 현재 `text-s` 가 §2 와 맞다 |
| G3 | 토글·칩 `text-s` | **KEEP CURRENT** + 문서 갱신 | doc | 현재 `sm` 버튼과 토글이 모두 `text-xs` 로 **밀도 위계가 일관**된다. 문서 §2 의 「컨트롤도 `text-s`」를 「밀도 높은 컨트롤(sm·토글)은 `text-xs`」로 고쳐 실물에 맞춘다 |
| G4 | 링크 밑줄 호버 `foreground` | **부분 적용 완료** | primitive | `hover:decoration-accent` **6곳만** 바꿨다 — `#CCC` → `#FFCD00` 은 둘 다 1.4~1.5:1 이라 호버가 바뀐 것을 알 수 없었다. **기본부터 옐로 2px 인 8곳은 유지** — 파일 다운로드·전자 날인의 브랜드 강조이고 글자는 검정이라 가독성에 영향이 없다. 밑줄은 장식이다 |
| G5 | select 화살표 직접 그리기 | **적용 완료** | token | 기본 화살표는 패딩 바깥·테두리 안쪽 끝에 붙어 오른쪽 여백이 먹지 않는다. 배경으로 깔아 왼쪽 글자 여백과 같은 14 만큼 띄웠다. `currentColor` 는 `data:` URI 안에서 쓸 수 없어 검정 고정인데, **검정 면 위 select 가 지금 없음을 확인**하고 그 조건을 문서에 남겼다 |
| G6 | 입력 포커스 표시 | **적용 완료** | token | 검정 테두리 + 같은 색 아웃라인 2px(21:1). 옐로 1.5:1 은 WCAG 가 포커스 표시에 요구하는 3:1 에 못 미친다. **문서가 「옐로는 포커스 링과 밑줄 강조에만」이라 규정하고 있어 그 줄도 고쳤다** — 같은 문서가 「옐로 글자는 1.5:1 로 읽히지 않는다」고 인정하던 내부 모순이다 |
| G7 | 체크박스·라디오 지면 반대색 | **적용 완료 + 확장** | token + refactor | 전역 규칙(`--check-fill` 기본 검정, 칩·검정 면 안 흰 채움)을 넣고 `CHOICE_SELECTED_VARS` 에 `--check-fill` 을 추가했다. **확장**: 색이 세 갈래였다 — 백오피스 옐로(`accent-accent` 7곳)·공개 검정(`accent-foreground` 5곳)·미설정(브라우저 기본색). 유틸 12곳을 지워 한 곳으로 모으고 예외는 탈퇴 동의(`accent-danger`) 하나만 남겼다 |
| G8 | 간격 팔레트 | **DROP (토큰 도입) + 문서·2곳 정리 완료** | doc + page | **초기 진단이 부정확했다** — 아래 §4-3. 「임의값 123곳」의 대부분은 `Band` 가 정한 섹션 패딩과 이미 40 으로 통일된 값이었다. 예전 토큰 20여 개를 도입할 근거가 없어 **토큰은 만들지 않고**, 문서를 실물에 맞추고 어긋난 2곳만 접었다 |
| G9 | 루트 글자 크기를 화면 폭에 매달기 | **적용 완료 + 하한 보정** (승인 2026-09-09) | token | `html { font-size: max(0.875rem, min(1rem, 100vw / 90)) }`, `lg` 이상. 하한 없이 넣었더니 1024 에서 루트 11.4 → 본문 **10px** 이라 요청으로 하한 14 를 넣었다(본문 12.25 에서 멈춘다). 하한이 `rem` 이라 사용자 기본 글자 크기 설정에 비례하는 부수 효과도 있다 |

## 4-1. 요청으로 추가된 결정 (G 목록 밖)

| 날짜 | 내용 | 계층 | 근거 |
|---|---|---|---|
| 2026-09-09 | **루트 축소에 하한 14** — `max(0.875rem, …)` | token | 1024 에서 본문이 10px 까지 내려가 읽기 부담스러웠다 |
| 2026-09-09 | **홈 브랜드 선언문 제목을 지면 폭에 유동시킨다** — `text-d2-fluid` = `clamp(40px, 6.6667vw, 96px)` | token + page | `text-h1-m sm:text-d2` 라 **640 에서 40 → 96 으로 점프**하고 그 뒤로는 루트 축소만 따랐다. 루트 축소는 `lg` 이상 전용이고 하한이 붙은 뒤 1024~1260 도 고정이라, 640~1260 이 통째로 비어 좁은 데스크톱에서 제목 한 글자가 지면의 6분의 1을 먹었다. `vw` 로 600~1440 을 연속으로 잇는다. 계수 6.6667vw = 96/1440 이라 정본 폭에서 `text-d2` 와 값이 같다. `rem` 을 섞지 않는다 — 루트 축소와 겹쳐 이중으로 줄어든다 |

홈은 「메인 기준」이 방침이므로 **선언문 제목 한 곳만** 바꿨다. 히어로(`text-d2-m lg:text-d2`)도
같은 점프를 갖고 있지만 요청 범위가 아니라 두었다 — 필요하면 같은 유틸리티를 쓰면 된다.

## 4-2. 선 정리 내역 (G12, 2026-09-09)

사용처를 전부 읽고 **한 변이면 구분선, 사방이면 윤곽**이라는 기준으로 갈랐다.
`divide-*` 도 선이므로 함께 셌다 — 처음 실측(94곳)에는 빠져 있었고 16곳이 더 있었다.

### 눈에 보이는 변화가 있는 곳

- **신청서 상세**(`QuoteApplicationDetail`) — 정의목록 19줄이 60% → 25% 로 **옅어진다.**
  행이 많은 화면이라 격자가 성기어 보이는 대신 밀도가 낮아진다. 가장 큰 시각 변화다.
- **표 머리행**(규약·개인정보·`DataTable`)과 **위저드 합계줄** — 40% → 검정으로 **진해진다.**
  `SpecTable` 이 이미 검정을 쓰므로 손으로 만든 표가 프리미티브와 같은 결이 된다.
- 나머지(15·20·30·50%)는 25% 와 육안 차이가 없다.

### 함께 고친 것

`SummaryPanel` 141행이 `border-t border-border/25 border-b border-border/15` 였다 —
**위는 진하게, 아래는 옅게** 하려던 것인데 `border-color` 는 속성이 하나라 나중 값이
위아래 모두에 적용된다. 의도가 처음부터 작동하지 않았다. `border-y border-border/25`
한 줄로 정리했다.

## 4-3. 간격 정리 내역 (G8, 2026-09-09)

### 초기 진단이 틀렸다

베이스라인에 「세로 간격 임의값 123곳」이라 적고 예전 팔레트(20여 토큰) 재도입을
예정했는데, 사용처를 열어 보니 **셋 중 하나도 임의값이 아니었다.**

| 처음 센 것 | 실제 |
|---|---|
| `py-10`·`py-12`·`py-14`·`py-16`·`py-20` 등 | 대부분 **`Band` 가 정한 섹션 패딩**이다(`lg` 56/64/80 · `md` 40/48/64 · `sm` 32/40). 규격이지 임의값이 아니다 |
| `mt-*` 60여 곳 | **`mt-10`(40)이 48곳으로 지배적**이다. 머리글→본문, 블록→블록, 선으로 가르는 섹션 사이가 모두 40 — 이미 통일돼 있었다 |
| 나머지 | 푸터·전면 안내 화면·빈 상태의 **자기 리듬** |

값 집합(40·48·56·64·80·96)도 예전 팔레트(`section-sm` 40 · `block` 48 · `section-md` 64 ·
`section-lg` 80 · `foot-top` 96)와 **사실상 같다.** 이름이 없을 뿐이었다.

### 그래서 토큰을 만들지 않았다

`--spacing-section-md` 같은 이름을 새로 도입하면 48곳 이상을 치환해야 하는데, 얻는 것은
「한 곳에서 조정 가능」뿐이다. 그 사이 `mt-10` 과 `mt-section` 두 어휘가 공존하는 구간이
생겨 오히려 갈래가 늘어난다. **이미 일관된 값에 새 이름을 씌우는 것은 정리가 아니다.**

예전 팔레트에서 되살리지 않기로 한 것도 분명해졌다 — `article-search`(90)·`tabbar`(72)
처럼 **한 화면 전용 값**은 시스템 토큰이 아니라 그 화면의 사정이다.

### 실제로 고친 것 — 같은 역할에 값이 갈린 2곳

| 자리 | 전 | 후 | 근거 |
|---|---|---|---|
| `app/rates/page.tsx:232` 머리글 → 첫 섹션 | 56 (`mt-14`) | **40** (`mt-10`) | 「머리글 → 본문 40」은 문서 규칙이자 지배값이다 |
| `app/features/page.tsx:272` 밴드 안 섹션 사이 | 64/80 (`mt-16 sm:mt-20`) | **48** (`mt-12`) | 같은 역할을 `rates` 는 48(`pt-12`)로 준다. 둘 중 하나로 접었다 |

### 문서를 실물에 맞췄다

기존 서술 「간격은 세 값만 쓴다 — 16 · 12 · 40」은 **틀렸다.** 실제로는 섹션 패딩을
`Band` 가, 머리글 안쪽을 `PageHead`(16)·`SectionHead`(12)가 정하고, 손으로 주는 값은
40 과 48 둘이다. 가르는 기준(**선이 구분을 맡으면 40, 여백만으로 가르면 48**)과
자기 리듬을 갖는 예외 셋(푸터·전면 안내 화면·빈 상태)까지 §밴드 리듬에 적었다.

## 4-4. 폼·컨트롤 정리 내역 (3단계, 2026-09-09)

### 판정 두 개를 정정했다

- **G1(버튼 호버)** — 「현재 호버 피드백이 아예 없다」가 근거였는데 **틀렸다.**
  `btnClass` 의 네 변형이 모두 호버를 갖고 있다(`primary` 진한 검정 · `secondary` 검정
  채움 반전 · `tertiary` 밑줄 · `danger` 빨강 채움). 이미 한 곳에 모여 일관적이라
  **KEEP CURRENT** 로 바꾸고 문서에 명문화만 했다. 옐로 통일은 브랜드 표현 변경이므로
  요청 없이 하지 않는다.
- **G7(체크박스)** — 「`accent-color` 설정이 하나도 없다」는 절반만 맞았다. `globals.css`
  에는 없었지만 **유틸리티로 12곳이 지정하고 있었다.** 그래서 단순 RESTORE 가 아니라
  갈래를 없애는 리팩터가 됐다.

### 고친 것

| 항목 | 전 | 후 | 근거 |
|---|---|---|---|
| 입력 포커스 (G6) | 옐로 아웃라인 2px | **검정 테두리 + 검정 아웃라인 2px** | 옐로는 오프화이트 지면에서 **1.5:1** — 초점이 어디인지 보이지 않는다. WCAG 는 포커스 표시에 3:1 을 요구한다. 검정은 21:1 |
| `select` 화살표 (G5) | 브라우저 기본 | **직접 그린 셰브런**, 오른쪽 14 | 기본 화살표는 패딩 바깥·테두리 안쪽 끝에 붙어 오른쪽 여백이 먹지 않는다 |
| 체크박스·라디오 (G7) | 옐로 7 · 검정 5 · 브라우저 기본 다수 | **전역 규칙 하나** (지면과 반대색) + 예외 1 | 옐로 채움은 「선택 = 검정 채움」과 어긋나고 1.5:1 이다. 유틸 12곳을 지웠다 |
| 링크 밑줄 호버 (G4) | `hover:decoration-accent` 6곳 | **`hover:decoration-foreground`** | `#CCC` → `#FFCD00` 은 둘 다 1.4~1.5:1 이라 호버가 바뀐 것을 알 수 없다 |
| `field-base` 정의 | **두 번 정의**(478·501행) | 하나로 병합 | 중복 |

**손대지 않은 것** — 기본부터 옐로 2px 인 밑줄 8곳(파일 다운로드·전자 날인). 브랜드
강조가 목적이고 글자는 검정이라 가독성에 영향이 없다. 밑줄은 장식이다.
체크박스 예외 하나(`accent-danger`, 회원 탈퇴 동의)도 남겼다 — 되돌릴 수 없는 동작이라
색으로 경고하는 것이 맞다.

### 문서 내부 모순을 고쳤다

`design-system.md` 금지 사항에 **「옐로는 포커스 링과 밑줄 강조에만」** 이라 적혀 있었다.
그런데 같은 줄이 **「흰 지면 위 옐로 글자는 1.5:1 로 읽히지 않는다」** 고 인정한다 —
링도 배경 대비가 필요하므로 같은 이유로 포커스에 쓸 수 없다. 「포커스 링에도 쓰지
않는다(WCAG 3:1 미달)」로 고치고 정정 시점을 남겼다.

### 눈에 보이는 변화

- **모든 입력칸의 포커스 링**이 옐로 → 검정. 가장 넓게 퍼지는 변화다
- **백오피스 체크박스 7곳**이 옐로 → 검정
- 설정이 없던 체크박스들이 **브라우저 기본색(사파리 파랑) → 검정**
- `select` 에 셰브런이 생기고 오른쪽 여백이 잡힌다
